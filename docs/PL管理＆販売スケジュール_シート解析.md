# 「PL管理＆販売スケジュール」シートの解析メモ

日別目標機能の実装根拠。ユーザーのGoogleスプレッドシート（社内運用のPL管理シート）を
CSVエクスポートで取得し、**データが入っている92日分すべてで数式を逆算・検算**した結果。

> **⚠ このリポジトリは公開されています。** シートのURL（ドキュメントID）・実際の原価・
> 売価・手数料の数値はここには書きません（原価は競合に知られたくない情報です）。
> 実データが必要な場合は `_ローカル専用（共有しない）/` に置くか、シート本体を参照してください。
> ここには**実装に必要な数式と構造だけ**を残します。

取得方法（公開設定のシートなら認証なしで読める）:

```
https://docs.google.com/spreadsheets/d/<ドキュメントID>/export?format=csv&gid=0
```

## シートの構造

- 1行目＝パラメータ行：`A1`にASIN、`D1/E1/F1`に`imp`、`I1`にFBAコスト（円/個）、
  `J1`にコンサル手数料率（%）
  - `imp` は「Amazon実績から取り込む列」の意味と解釈した（売上・個数・アクセス数）
- 2行目＝ヘッダー
- 3行目以降＝日別（半年分の184日。うち92日にデータが入っていた）
- タブは1枚だけ（`gid=0`）

## 列と数式（検算結果つき）

| 列 | 項目 | 種別 | 検算 |
|---|---|---|---|
| A | 日付 | — | |
| B | 曜日 | 日付から自動 | |
| C | 売価 | 入力（期間中13回変動） | |
| D | P(売上) | 実績取込 | 売価×個数と一致するのは **71/92日** のみ（1日に複数価格帯で売れた日があるため） |
| E | VQ(個数) | 実績取込 | |
| F | PV(アクセス数) | 実績取込 | |
| G | 原価合計 | 原価単価 × 個数 | |
| H | 販売手数料 | **販売手数料単価 × 個数** | **92/92 一致** |
| I | FBAコスト | FBA単価 × 個数 | |
| J | コンサル手数料 | **売上 × 率(%) × 1.1（税込）** | **92/92 一致** |
| K | VC(変動費) | G＋H＋I＋J | **92/92 一致** |
| L | MQ(粗利額) | P − VC | **92/92 一致** |
| M | M(粗利率) | MQ ÷ P | **67/67 一致** |
| N | CPA(税込) | 売価に対してほぼ一定の率（4つの売価すべてで同率） | H＝N×個数 なので、実質「1個あたりの販売手数料（税込）」として使われている |

## 売価ごとに原価・販売手数料が変わる（＝価格マスタが必要な理由）

このシートで最も重要な発見。**同じ子ASINでも売価によって原価と販売手数料が違う**
（実データでは4つの売価が使われ、原価は2種類、販売手数料は売価ごとに4種類あった）。

さらに**売価は半年で13回切り替わっていた**（セール期間ごとに上げ下げする運用）。
このため、

1. アプリ側に**価格マスタ（子ASIN × 売価 → 原価・販売手数料）**を新設し、
2. **「期間を指定して売価を一律入力」**という一括入力を用意した。

## アプリ実装との対応

- **実績（`imp`）→ 目標**：アプリは「目標」を作るツールなので、売上は取込ではなく
  **売価 × 目標個数** で計算する。入力するのは 売価・目標個数・目標アクセス数の3つだけ。
- 原価・販売手数料は価格マスタから売価で引く。**売価がマスタに無い日は「⚠ マスタ未登録」**
  として集計から除外する（シートが `#N/A` になっていた挙動に対応）。
- コンサル手数料は率(%)＋税率(%)で持つ。月次シミュ側の子ASINが持つ
  `consultFee`（円/点）とは**別物**なので注意。

## 検証について

Playwrightの検証では、**実シートの2日分（売価と個数）を入力して、
売上・原価合計・販売手数料・コンサル手数料・VC・MQ・粗利率の7項目が
シートの値と完全に一致すること**をアサートしている。
期待値は公開を避けるためここには書かない（テストコードもスクラッチで破棄済み）。
再検証する場合はシート本体から任意の日を選び、同じ7項目を突き合わせれば足りる。
